**연관 스크립트**: [[RunUnit]] · [[RunData]] · [[JudgeResult]] · [[UnitGradeTable]] · [[UIInGameField]] · [[UIInGameBattle]] · [[InGameScene]]

런 동안 유지되는 유닛 명부. 보관함(bench)과 전장(field) 9칸을 한 주체가 소유한다.

## 2026-09-11-0 — 신규 생성 (유닛 보관·3합 승급 1단계)

### 개요

사용자 요청으로 코어 루프를 바꾼다. 스핀 결과가 전장에 바로 내려앉던 방식을 폐기하고,
유닛을 **보관함에 쌓았다가 드래그로 배치**하며 **같은 유닛 3기를 모으면 승급**하는 구조로 간다.

이 변경은 기획 이탈이 아니다. GDD 「13 정직한 리스크 · 치명」이 스스로 적어둔 탈출구다.

> "릴 좌표 = 전장 좌표가 플레이어 주도권을 없앨 수 있다. … 스왑을 다 써도 재미없으면 **이 아이디어는 버립니다.**"

게다가 완화책으로 적힌 **스왑은 실제로 미구현이었다** — `RunData.m_SwapCount`를 소비하는 코드가
프로젝트 전체에 0곳이다(HUD 핍만 그려진다). 즉 플레이어 개입 수단이 현재 0개다.

### 확정된 설계 결정 (2026-09-11 사용자)

| 갈림길 | 결정 | 이유 |
|---|---|---|
| 유닛 수명 | **런 내내 누적. 전투에서 죽어도 다음 웨이브에 부활** | 연차가 오를수록 적이 22배로 강해지는 곡선을 따라갈 성장 축이 지금까지 없었다 |
| 판정 전력의 환산 | **1성만 지급. 승급은 3합으로만** | 기존 자동 등급 전환은 폐기. 9칸 상한 때문에 전력 63 초과분이 버려지던 결함과, 그걸 메우려 넣은 자동 등급 장치가 함께 사라진다 |

### 승급 규칙

- 같은 `SymbolType` + 같은 `Grade` **3기**가 모이면 1기가 `Grade + 1`이 되고 나머지 2기는 사라진다.
- **보관함과 전장을 통틀어 센다.** 그래서 이 클래스가 둘 다 소유한다 — 소유자를 나누면
  "보관함 2기 + 전장 1기"에서 어느 쪽도 3기를 못 세어 승급이 조용히 안 일어난다.
- **재료 중 전장에 있던 것이 있으면 승급체가 그 칸을 잇는다.** 안 그러면 배치해둔 유닛이
  승급할 때마다 보관함으로 빠져 플레이어가 매번 다시 놓아야 한다.
- **연쇄한다.** 1성 3기 → 2성 1기가 기존 2성 2기와 합쳐져 곧바로 3성이 되는 경우가 있어
  `MergeAll()`이 더 이상 안 될 때까지 반복한다. 한 번만 돌리면 두 번째 승급이 다음 스핀까지 밀린다.
- `UnitGradeTable.maxGrade`(현재 3성)에 도달한 유닛은 더 흡수하지 않는다.

### 공개 API

| 메서드 | 하는 일 |
|---|---|
| `Init()` | `UnitGradeTable`에서 상한을 읽고 전장·보관함을 비운다 |
| `AddUnit(int _symbolType)` | 1성으로 보관함에 넣고 **곧바로 승급을 검사한다**(호출부가 따로 안 불러도 된다) |
| `MergeAll()` | 가능한 승급을 전부 수행하고 횟수를 돌려준다 |
| `MoveBenchToField(int _benchIndex, int _cell)` | 점유된 칸이면 **자리를 맞바꾼다**(조용히 실패하지 않는다). 이동 후 승급 검사 |
| `MoveFieldToBench(int _cell)` | 전장에서 내린다. 총 보유가 안 바뀌므로 승급 검사는 하지 않는다 |
| `SwapField(int _from, int _to)` | 전장 두 칸 교환. 한쪽이 비어 있어도 성립한다 |
| `GetFieldPower()` | 전장 유닛의 전력 합. 1성 = 1.0으로 적 전력과 같은 눈금 |
| `ArrangeFieldByGrade()` | **성급 높은 순으로** 전장 9칸을 세운다. 배치를 안 해도 전투가 성립하게 하는 안전망 |
| `GetFieldUnit` · `GetBenchUnit` · `fieldCount` · `benchCount` · `listBench` · `IsFieldFull` | 조회 |

### 코드 규칙 메모

정수 동등 비교를 `==`로 쓰지 않는다는 규칙 때문에 `IsSameKind`·`SwapField`가
`>= && <=` 형태로 쓰여 있다. 프로젝트의 `UnitGradeTable.GetRecord`가 이미 같은 방식이다.

### ⬜ 아직 안 한 것 (이 단계의 경계)

1단계는 **순수 데이터 구조까지**다. 아래는 연결되지 않았다.

- `RunData`가 이 명부를 들고 있지 않다 — 아직 아무도 생성하지 않는다
- `Judge.BuildSummon()`의 **자동 등급 전환이 그대로 남아 있다**. 위 결정대로면 제거해야 하지만,
  같은 작업에서 `UIInGameField.ShowSummon`·`UIInGameBattle.SpawnAllies`까지 함께 갈아야 해서 2단계로 미뤘다.
  → **지금은 승급 경로가 둘 다 코드에 존재한다.** 2단계를 끝내기 전에는 이중 상태다
- 전투가 `JudgeResult`를 읽는다 — 전장 배치를 읽도록 바꿔야 한다
- 보관함 UI와 드래그 앤 드롭이 없다(씬·프리팹 작업이라 Codex 몫)
- **Unity 컴파일 확인을 못 했다** — Codex가 같은 에디터에서 베이스라인 QA 중이라
  에디터를 동시에 쓰지 않기로 한 규칙에 따라 대기 중이다

## 2026-09-12-0 — `FillFieldFromBench()` → `ArrangeFieldByGrade()`

### 증상

전장 전력이 보유량에 비해 낮았다. Play Mode 실측에서 Poker 6연차 3웨이브의 전장 전력이 30.6인데,
같은 보유량을 최선으로 배치하면 49까지 나올 수 있는 상태였다.

### 원인

`FillFieldFromBench()`가 **빈 칸을 보관함 앞쪽부터** 채웠다. 성급을 보지 않아서
**3성이 보관함에 남고 1성이 전장에 서는** 경우가 생긴다. 전장이 9칸뿐이라 그 손해가 곧 전투력이다.

시뮬레이션(`scratchpad/merge_rate.py`, 심볼 균등 분포 가정)에서 6연차 3웨이브 시점 전장 전력:

| | 심볼 6종 | 9종 | 13종 |
|---|---:|---:|---:|
| 최선 배치(강한 9기) | 62.5 | 59.5 | 49.0 |
| **앞쪽부터 채우기(기존)** | 37.9 | 31.7 | **25.0** |

같은 보유량인데 배치만 바꿔도 거의 2배다. 실측 30.6도 낮은 쪽에 가까웠다.

### 수정

전장 + 보관함을 한 목록으로 모아 **성급 내림차순으로 전장 9칸을 다시 세운다.** 넘치면 보관함으로.

- `List.Sort`를 쓰지 않고 **성급별로 훑어 담는다** — `Sort`는 불안정 정렬이라 같은 성급의 순서가
  매번 뒤바뀌고, 그러면 스핀마다 화면의 유닛이 이유 없이 자리를 옮긴다
- 유닛이 9칸보다 적으면 **뒤쪽 칸을 비운다** — 안 비우면 앞으로 옮겨간 유닛이 원래 칸에도 남는다
- 반환값 의미가 "채운 수" → **"자리가 바뀐 칸 수"**로 바뀌었다(연출 판단용). 호출부는 반환값을 쓰지 않는다

### ★ 임시 조치다 — 제거 조건이 있다

전장 전체를 다시 세우므로 **플레이어가 직접 놓은 배치를 덮어쓴다.** 지금은 배치 수단이
아예 없어서(드래그 미구현) 순이득이지만, **`UIInGameFieldSlot`에 드래그 핸들러가 붙는 시점에
"빈 칸만 채우는" 쪽으로 좁혀야 한다.** 코드 주석에도 같은 조건을 적어뒀다.

### 호출부

`InGameScene.cs:205`(전투 시작 전) · `InGameScene.cs:471`(스핀 직후) 두 곳. 이름만 바뀌었다.

### ✅ 검증 통과 (2026-09-12, Codex)

보고서: `Temp/balance-sample-2026-09-12.md`

### ⬜ 아직 모르는 것 — 게임 결과에 얼마나 기여하는가

**로직이 정확하다는 것과 런이 길어진다는 것은 다르다.** 3순위였던 밸런스 표본(원칙 A/B 장기 측정,
이전 6-3 비교)은 사용량 부족으로 생략됐다. 즉 **전장 전력이 실제로 올랐는지, 종료 연차가
밀렸는지는 측정되지 않았다.** 시뮬 예측(13종 기준 25 → 49)은 여전히 예측이다.

Play Mode의 전력 13.8은 5스핀 시점 값이라 6연차 비교 대상이 아니다.
