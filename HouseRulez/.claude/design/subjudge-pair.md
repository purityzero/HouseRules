# 부판정 짝(PAIR_COUNT) 구현 스펙

## 2026-08-27-0 — 개요

GDD §06의 부판정 짝을 판정기가 그대로 옮길 수 있는 수준으로 확정했다. 결론 두 줄:

1. **짝의 정의는 "보드 전체(3×3) · 같은 이질 심볼 2개 = 1짝 · 스핀당 최대 2짝"으로 확정한다.** GDD 본문이 특정하지 않은 범위·단위를 기존 코드 관례와 6종족 일관성 기준으로 메웠다.
2. **GDD의 `부판정 짝` 열(0.51 / 0.74 / 0.86)은 재현 불가능하며, 시뮬레이션 출력이 아니라 "총 전력을 5.37로 평평하게 두고 5.5로 나눈" 역산값이다.** 근거는 §3. 따라서 **짝당 계수 5.5도 함께 무효**이며, 같은 설계 의도(첫 약탈 −12%)를 실제 규칙으로 다시 풀면 **4.25**가 나온다.

`slot-house.md` §10-7이 남긴 미결(내 계산 0.66짝 vs GDD 0.51짝)을 이 문서가 닫는다. 그때의 0.66은 계산 실수가 아니라 **맞는 값이었고, 어긋난 쪽은 GDD였다.**

## 1. 확정 정의

### 1.1 규칙 (판정기가 그대로 옮길 것)

> **주판정** — 판정 단위(라인 / 손 / 면자) 안에 이질 심볼이 하나라도 들어가면 **그 단위는 주판정에서 제외**한다.
> **부판정** — 보드 **3×3 전체**를 훑어, **같은 이질 심볼 2개를 1짝**으로 센다. 같은 심볼이 3개면 1짝, 4개면 2짝(내림). **스핀당 최대 2짝.**
> **전력** = 주판정 전력 + (짝 개수 × 4.25)

확정한 항목을 하나씩 못박으면:

| 쟁점 | 확정 | 근거 |
|---|---|---|
| 범위 | **3×3 전역** (라인 아님) | §1.2 — 근거 3건 |
| 짝의 단위 | **같은 심볼** 2개 (같은 종족 2개가 아님) | 짝(對)은 "같은 것"이다. 같은 종족의 서로 다른 두 심볼은 짝이 아니다. 또 종족 단위로 세면 계수를 어떻게 잡아도 혼혈이 순혈보다 세진다(§4.3) |
| 3개가 같으면 | **1짝** (`k / 2` 내림) | 심볼 하나는 짝 하나에만 쓰인다. 화투 짝 문법과 동일 |
| 4개가 같으면 | **2짝** | 위와 동일 |
| 상한 적용 위치 | **스핀 전체에 1회** (라인별 아님) | 전역 규칙이라 라인 개념이 없다. GDD "최대 2짝" 문언 그대로 |
| 자기 종족 심볼 | **절대 짝에 못 들어간다** | GDD "이질 심볼**끼리는** 짝 판정" |
| 어느 단위에서 세나 | **주판정 결과와 무관하게 항상 전체에서** | 전역이므로 "제외된 라인"을 식별할 필요 자체가 없다 |
| 짝당 전력 | **4.25** (GDD 기재 5.5에서 변경) | §3 / §4.2 |

### 1.2 왜 라인이 아니라 전역인가 — 근거 3건

**(가) GDD 자신의 어휘가 그렇다.** §04 376줄이 네 종족의 판정을 분류하며 **"화투는 전역 짝 판정"**이라고 쓴다. 이 문서에서 `짝 판정`은 전역 문법을 가리키는 고유 명칭이고, §06이 부판정에 붙인 이름도 똑같이 `짝 판정`이다. 라인 짝을 의도했다면 §04의 분류와 충돌한다.

**(나) 라인 범위로 잡으면 종족마다 부판정 세기가 달라진다 — 이게 결정적이다.** 판정 단위가 종족마다 다르기 때문이다(체스·장기·포커 8라인 / 슬롯 5라인 / 화투 3열 / 마작 3면자). 같은 풀 8에서 측정한 짝 개수:

| 범위 | 체스(8라인) | 슬롯(5라인) | 격차 |
|---|---|---|---|
| 8라인 기준 | 0.587 | — | — |
| 5라인 기준 | — | 0.405 | **−31%** |
| **전역** | **0.659** | **0.659** | **0** |

라인 범위를 쓰면 슬롯은 같은 전리품을 받고도 부판정 보상이 체스의 69%에 그친다. 이는 `slot-house.md` §7.4가 세운 결론 — *"표준 규칙을 쓰면 슬롯의 혼혈 곡선이 체스와 사실상 같다 → 밸런싱 축이 하나도 늘지 않는다"* — 를 정면으로 깬다. **전역 규칙은 판정 단위를 안 보므로 6종족에서 문자 그대로 같은 코드가 돈다.**

**(다) 구현이 단순하고 화면에서 셀 수 있다.** 전역은 9칸을 한 번 훑는 카운트 배열 하나면 끝난다. `SlotLineTable`을 참조하지 않으므로 주판정과 완전히 독립적으로 붙는다. 플레이어 입장에서도 "보드 어디든 같은 외지 심볼 2개"는 라인을 몰라도 셀 수 있다 — 라인 범위였다면 "칸 0과 칸 5는 같은 라인이 아니라서 짝이 아니다" 같은 설명이 필요해진다.

### 1.3 의사코드

```csharp
// 부판정 — Judge.csv PatternType == PAIR_COUNT
// 주판정과 완전히 독립. 라인/손/면자 같은 판정 단위를 전혀 보지 않으므로 6종족 공용이다.
// _board 는 최종 확정된 3×3 보드 9칸의 symbolType, _purePoolCount 는 HouseRecord.PoolCount.
private int JudgePairCount(int[] _board, int _purePoolCount)
{
    Dictionary<int, int> dicForeignCount = new Dictionary<int, int>();

    for (int index = 0; index < _board.Length; ++index)
    {
        int symbolType = _board[index];

        // 자기 종족 심볼은 짝에 들어가지 않는다 (GDD §06 "이질 심볼끼리는")
        if (symbolType < _purePoolCount)
            continue;

        if (dicForeignCount.ContainsKey(symbolType) == false)
            dicForeignCount.Add(symbolType, 0);

        dicForeignCount[symbolType] += 1;
    }

    int pairCount = 0;

    foreach (KeyValuePair<int, int> pair in dicForeignCount)
    {
        // 2개 = 1짝, 3개 = 1짝, 4개 = 2짝
        pairCount += pair.Value / 2;
    }

    int pairMax = GameConfigTable.GetInt("SubJudgePairMax");

    if (pairCount > pairMax)
        pairCount = pairMax;

    return pairCount;
}

// 최종 전력 합산
float pairPower = JudgePairCount(board, houseRecord.PoolCount)
                  * GameConfigTable.GetFloat("SubJudgePairPower");
float totalPower = mainJudgePower + pairPower;
```

**하이라이트 규칙**: 주판정은 라인 단위로 칸을 튕기지만(`UIHouseSlotMachine.PlayWinEffect()`), 짝은 라인이 아니라 **칸 2개짜리 묶음**이다. 짝을 이룬 두 칸만 묶어서 표시하고, 라인 하이라이트와는 다른 연출을 써야 플레이어가 두 판정을 혼동하지 않는다.

## 3. 역산 과정 — GDD 0.51은 재현되지 않는다

### 3.1 1단계: GDD 안에 정답 코드가 있는지 먼저 뒤졌다 → 없다

`reel_of_four_houses_GDD.html` 746~970줄의 `<script>`를 전부 읽었다. `judge()` 함수는 체스(805줄) · 장기(818줄) · 포커(831줄) · 화투(846줄) **주판정 4종만** 구현하고, 데모는 `POOL_N = 6`(787줄)으로 **항상 순혈만 굴린다.** 이질 심볼도, 짝 판정도, 부판정 레이어도 코드에 존재하지 않는다. 슬롯·마작은 데모 자체에 없다(문서가 4종족 시점).

**즉 GDD 안에 짝 판정의 정답 구현은 없다.** `PurityCurve` 표는 이 데모가 아니라 외부에서 만들어진 수치다.

### 3.2 2단계: 척도 검증 — 주판정은 소수점까지 맞는다

규칙을 역산하기 전에 내 시뮬레이터가 GDD와 같은 척도인지부터 확인했다(30만 시행, seed 20260827):

`(순혈 종수 / 전체 풀)³`로 라인이 죽는 모델이 GDD와 정확히 같다. **주판정 4행이 전부 맞으므로, 어긋나는 건 짝 세는 규칙 하나뿐이라는 게 확정된다.**

### 3.3 3단계: 규칙 전수 탐색 — 720개 조합, 전부 실패

6개 축을 전수 조합(범위 6 × 단위 3 × 세는 법 5 × 상한 3 × 대상 2 × 라인필터 2, 중복 제거 후 유효 조합)해 풀 8/10/13에서 동시에 0.51 / 0.74 / 0.86을 내는 규칙을 찾았다. **오차 합(3행 절대오차)이 가장 작은 것도 0.115였다** — 행당 평균 0.038로, 30만 시행의 표준오차(±0.002)의 19배다.

**어떤 규칙도 세 값을 동시에 못 맞춘다.** 이유는 형태에 있다 — GDD의 증가 폭은 풀 8→10에서 **+45%**, 10→13에서 **+16%**로 급했다가 급히 꺾인다. 반면 실제 짝 규칙은 상한 2에 눌려 완만하게 포화하므로(+28%→+26% 또는 +32%→+8%) 이 꺾임을 못 만든다. 상한을 풀거나 조이거나, 범위를 넓히거나 좁혀도 곡선의 *모양*이 안 맞는다.

### 3.4 4단계: 진짜 답 — 그 열은 시뮬레이션이 아니다

GDD 표의 세 값을 나눠보면 정체가 드러난다.

```
(총 전력 − 주판정 전력) ÷ 5.5
풀 8 :  (5.38 − 2.56) / 5.5 = 0.5127  → 0.51  ✓
풀 10:  (5.39 − 1.32) / 5.5 = 0.7400  → 0.74  ✓
풀 13:  (5.35 − 0.60) / 5.5 = 0.8636  → 0.86  ✓
```

**세 행 전부 소수 둘째 자리까지 정확히 떨어진다.** 그리고 `총 전력` 열은 5.38 / 5.39 / 5.35 — 주판정이 2.56에서 0.60으로 **4.3배 줄어드는 동안 총합은 ±0.4% 안에서 평평하다.**

독립적으로 시뮬레이션한 짝 개수가 주판정의 감소분을 5.5로 나눈 값과 세 행 모두 우연히 일치할 확률은 사실상 0이다. 실제로 §3.3의 어떤 후보 규칙도 이런 평평한 총합을 못 만든다(예: 1순위 규칙의 총 전력은 5.66 / 5.28 / 5.58로 편차가 GDD의 9배).

역으로 상수 T를 두고 `짝 = (T − 주판정)/5.5`를 풀면:

| 가정한 T | 풀 8 | 풀 10 | 풀 13 |
|---|---|---|---|
| 5.35 | 0.504 | 0.733 | 0.863 |
| **5.365 (최적)** | **0.506** | **0.735** | **0.864** |
| 5.38 | 0.510 | 0.739 | 0.868 |
| **GDD 기재** | **0.51** | **0.74** | **0.86** |

최적 상수 **T = 5.365**에서 3행 절대오차 합이 **0.011**(행당 0.004)로, 반올림 오차 수준이다. §3.3 최선 규칙(0.115)의 **10분의 1**이다.

> **결론: `부판정 짝` 열은 관측값이 아니라 "총 전력을 5.37 언저리로 평평하게 만들려면 짝이 몇 개여야 하는가"를 거꾸로 푼 목표값이다.** 짝당 5.5도 같은 역산의 산물이므로 독립적 근거가 없다. GDD는 Draft 0.1이고, §06 본문의 주장(첫 약탈 −12%, 이후 평평)이 먼저 있고 표가 그 주장에 맞춰진 것으로 보인다.

## 4. 계수 재산정 — 왜 5.5가 아니라 4.25인가

### 4.1 5.5를 그대로 쓰면 GDD가 경고한 실패가 그대로 터진다

GDD §06은 *"계수를 더 올리면 전원이 혼혈로 직행한다"*고 스스로 경고한다. 확정 규칙(전역·같은 심볼·최대 2짝)에 **계수 5.5를 그대로** 얹어 6종족을 돌린 결과(30만 시행):

| 종족 | 순혈 전력 | 1회 약탈 총 전력 | 순혈 대비 |
|---|---|---|---|
| 체스 | 6.11 | 6.20 | **101.5%** |
| 슬롯 | 6.25 | 6.27 | **100.4%** |
| 화투 | 6.20 | 6.19 | 99.9% |
| 장기 | 6.29 | 5.98 | 95.1% |
| 포커 | 6.25 | 5.39 | 86.2% |
| 마작 | 6.27 | 5.33 | 85.0% |

**체스·슬롯은 약탈하면 릴 전력이 오히려 오른다.** 여기에 코어 1개와 `이방인` 각인까지 얹히면 선전포고가 무손실 이득이 되어, 화친·조공이라는 선택지가 통째로 죽는다. **5.5는 쓸 수 없다.**

### 4.2 설계 의도를 그대로 두고 계수만 다시 푼다

GDD §06에서 살릴 것은 숫자가 아니라 주장이다. 세 가지 중:

1. **"첫 약탈에서 −12%"** — §06 본문에 두 번, §07 서사("릴 전력 −12%를 코어 하나로 갚는 구조")에 한 번 인용된 **핵심 상수. 유지한다.**
2. **"봉우리(적당한 혼혈이 최적)를 만들지 않는다"** — 설계상 가장 중요한 제약. **유지한다.**
3. "그 뒤로는 평평하다" — 역산의 결과물이며, 그대로 두면 **2·3회 약탈이 릴 비용 0**이 되어 "전원이 3회 약탈"이 정답이 된다(1번 실패의 완만한 버전). **포기한다.** → §6

체스 행 기준으로 `풀 8 총 전력 = 순혈 × 0.88`을 만족하는 계수를 풀면 **c = 4.25**다. 이 값에서 풀 8 총 전력은 **5.38**로 GDD 기재값과 정확히 같아진다.

### 4.3 다른 정의를 골랐다면 (기각 사유)

### "평평"을 포기하는 것이 설계상 손해가 아닌 이유

평평한 곡선은 *2회·3회 약탈의 릴 비용이 0*이라는 뜻이다. 그러면 첫 약탈만 −12%를 내고 나머지는 공짜로 코어 2개를 더 받게 되어, **3회 약탈이 언제나 정답**이 된다. 이는 GDD가 §06에서 경고한 "전원이 혼혈로 직행"의 완만한 형태다.

확정 규칙의 −12% / −15% / −19%는 약탈 한 번마다 한계 비용이 붙어, "얼마나 깊이 들어갈 것인가"가 매 연차 실제 결정이 된다. **§06이 지키려던 것(혼혈은 순손해, 봉우리 없음)은 그대로 지켜지고, 지킬 이유가 없던 것(평평)만 빠진다.**

### 7.2 그러나 종족 간 혼혈 비용 편차가 크다 (미결)

- 주판정 감쇠도 `(순혈/전체)³`이라 풀이 큰 쪽이 덜 깎인다.
- **두 효과가 서로 상쇄되지 않는다.** 체스는 주판정 3.53을 잃고 2.80을 돌려받지만, 포커는 2.17을 잃고 1.01만 돌려받는다.

계수를 어떻게 잡아도(3.0 ~ 5.0 전 구간 확인) 편차 폭은 16~20%p로 거의 안 줄어든다 — **구조적이라 단일 계수로는 못 맞춘다.** 균일화하려면 종족별 계수(위 표 마지막 열, 2.74~5.98)가 필요한데 이는 밸런싱 축을 하나 늘리는 일이고, **GDD에 근거가 없는 기획 결정**이라 여기서 정하지 않는다. → §8-1

## 8. 문서에 없어서 확인이 필요한 부분

### 8-1. 종족별 혼혈 비용 편차를 균일화할 것인가 — **승인 필요 (최우선)**

§7.2 그대로. 두 선택지이며 어느 쪽도 GDD에 근거가 없다.

- **(A) 단일 계수 4.25 유지** — 밸런싱 축이 안 늘고 구현이 한 줄. 대신 화투는 약탈이 거의 공짜(−5.5%)라 무조건 선전포고, 마작은 −23%라 사실상 순혈 강제. *종족 성격으로 읽을 여지는 있다 — 마작은 이미 `mahjong-house.md` §5에서 "순혈로만 완성되는 종족"으로 확정됐으므로 −23%가 오히려 정합적이다.*
- **(B) 종족별 계수** — `HouseTable.csv`에 `SubJudgePairPower` 컬럼 추가(2.74 / 4.25 / 4.32 / 4.69 / 5.97 / 5.98). 전 종족 −12% 균일. 대신 종족당 튜닝 파라미터가 하나 늘어난다.

(A)를 기본값으로 두고 이 문서를 썼다. 뒤집으려면 이 항목만 바꾸면 되고 §1의 정의는 영향받지 않는다.

### 8-2. 약탈 1회가 심볼 몇 종을 주는가 — **GDD 내부 모순**

`DiplomacyTable`(§06)은 승리 보상을 **"상대 심볼 1종 + 코어 1개"**로 적는다. 그런데 같은 절의 `PurityCurve`는 6 → 8 → 10 → 13, 즉 **+2 / +2 / +3종**이다. 둘이 안 맞는다.

- "1종"이 맞으면 곡선은 6 → 7 → 8 → 9여야 하고, 이 스펙의 모든 수치를 다시 계산해야 한다.
- 이 문서는 `PurityCurve` 쪽(+2/+4/+7)을 따랐다 — GDD가 실제로 수치를 제시한 쪽이기 때문이다.
- 세 번째 약탈만 +3인 이유도 불명이다(포커의 13에 맞추려고 13을 골랐을 가능성).

**어느 쪽이 맞는지 확인 필요.** 이건 구현 디테일이 아니라 기획 수치라 임의로 정하지 않았다.

### 8-3. 전리품 심볼이 `symbolType` 공간의 어디에 들어가는가 — 확인 필요

§2의 `symbolType >= PoolCount` 판정은 **전리품이 순혈 풀 뒤에 덧붙는다**는 전제에서만 성립한다. 현재 코드(`UIHouseSlotSymbol.cs:62`)는 `symbolType`을 `m_SpritePool`의 인덱스로 쓰고 `Mathf.Clamp`로 잘라내므로, 혼혈 상태에서 스프라이트 풀을 어떻게 합칠지가 아직 정해져 있지 않다. 구현 착수 시 이 구조부터 정할 것.

### 8-4. 짝의 화면 표시 — 미기재

GDD는 짝의 연출을 언급하지 않는다. §1.3에 "칸 2개 묶음, 라인 하이라이트와 다른 연출"이라고 적어뒀으나 이는 **구현 관례에서 도출한 제안**이지 문서 근거가 아니다. 마작이 면자 3묶음에 각각 다른 마커를 요구한 것(`mahjong-house.md` §2)과 같은 성격의 판단이 필요하다.

### 8-5. GDD 본문 수정 여부 — 사용자 판단

§6 표대로면 GDD §06의 표 1개(`PurityCurve` 4행 × 3열)와 본문 문장 1개("그 뒤로는 평평합니다")를 고쳐야 한다. **이 스펙 작업에서는 GDD를 건드리지 않았다.** 고칠지, Draft 0.1의 기록으로 남기고 스펙 문서만 정본으로 쓸지는 사용자 판단.

### 9.2 새로 필요한 것

- `GameConfigTable.csv` 신규 행 2개: `SubJudgePairPower = 4.25`, `SubJudgePairMax = 2`

- 짝 하이라이트 연출 (→ §8-4)

### 9.3 충돌 가능 지점

- **`IsLineMatched()`가 지금은 순혈을 전제한다.** 이질 심볼이 들어오면 라인을 죽여야 하는데 현재는 그냥 "다른 심볼"로 처리되어 조용히 통과한다 — 혼혈 구현 시 여기부터 손봐야 한다.
- **짝은 주판정과 셈 단위가 다르다.** 주판정은 라인(칸 3개), 짝은 칸 2개다. 하나의 순회로 합치려다 라인 안에서 짝을 세게 되면 §1.2(나)의 종족 편차 문제가 그대로 들어온다. **두 판정은 별도 패스로 유지할 것.**
- **명명 충돌** — `slot-house.md` §2.2가 경고한 `hwatu_03_cherry` ↔ `slot_01_cherry`. 짝은 `symbolType` 정수 동등 비교라 논리적 오판정은 없지만, **혼혈 보드에서 두 심볼이 나란히 뜨면 플레이어가 "짝인데 왜 안 세지?"로 읽는다.** 아트에서 실루엣이 갈려야 한다.
- 마작·화투는 판정 단위가 라인이 아니다(면자 3묶음 / 3열 손). §1.1의 "판정 단위에 이질이 끼면 제외"는 이 둘에도 그대로 적용되며, 마작은 `mahjong-house.md` §5의 "이질 1장이면 화료 원천 불가"와 이미 정합적이다.
