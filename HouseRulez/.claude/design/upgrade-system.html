업그레이드 시스템 구현 스펙#

작성일 2026-08-28 · 기획 경계 확정용 초판

이 문서에서 업그레이드는 하나의 기능명이 아니다. (A) 타이틀에서 접근하는 종족별 영구 메타 업그레이드, (B) 런 내부 동일 유닛 흡수 승급, (C) 런 내부 각인·코어를 분리해 구현 순서를 정한다. 2026-08-28 사용자 결정인 **“종족마다 업그레이드가 따로 있었으면 좋겠다”**를 최신 요구로 반영한다. 구체 재화·비용·노드 효과는 정해지지 않았으므로 만들지 않는다.

핵심 결론#

1. 최신 방향은 종족별 독립 업그레이드다#

사용자 최신 결정에 따라 업그레이드 화면과 진행도는 종족별로 분리한다. 다만 여섯 벌의 코드를 복제하는 뜻은 아니다.

  • 공용 화면·공용 저장 모델·공용 효과 적용기는 하나만 둔다.
  • 모든 노드와 진행도에 HouseKey를 붙인다.
  • 화면은 선택한 HouseKey의 노드와 진행도만 보여준다.
  • 한 종족의 구매/해금은 다른 종족의 진행도를 자동으로 올리지 않는다.

타이틀의 UpgradeButton은 다음 런에도 유지되는 종족별 영구 메타 업그레이드로 사용한다. 이 범위는 2026-08-28 사용자 확인으로 확정됐다. 런 내부 유닛 승급은 별도 B층으로 유지하며 영구 진행에 합치지 않는다.

2. 이 결정은 GDD의 초기 제한을 변경한다#

GDD §09는 초기 빌드의 메타 진행을 종족 해금 하나로 제한하고 영구 강화 트리를 명시적으로 제외한다. 현재 PlayerData도 선택 종족·해금 종족·마지막 접속 시각만 저장하도록 이 경계를 지킨다.

따라서 최신 요구를 영구 메타로 확정하면 다음이 바뀐다.

  • GDD §09의 “영구 강화 트리 제외”는 더 이상 현행 요구가 아니며 개정 기록이 필요하다.
  • PlayerData에 종족별 업그레이드 진행 저장이 추가된다.
  • eCurrencyType과 비용 저장은 재화가 결정된 뒤 추가된다. 지금은 빈 스텁을 임의로 채우지 않는다.
  • 프로토타입 클리어율은 메타 0 상태와 메타 적용 상태를 분리해 측정해야 한다.
  • 코어·각인은 계속 런 전용이다. 영구 메타 소유물로 승격하지 않는다.

이 문서가 확정하는 것은 종족별 분리 구조까지다. 영구 공격력·체력·스핀 횟수, 재화명, 비용, 노드 개수와 효과량은 아직 승인되지 않았다.

3. 런 내부 흡수 승급은 별도 시스템이다#

GDD가 확정한 최소 재미 검증 단위는 체스 오토배틀 + 흡수 승급이다. 이 승급은 한 판이 끝나면 사라지는 런 상태이며 PlayerData가 아니라 RunData 계통이 소유한다.

4. 각인과 코어는 승급의 다음 단계이며 서로 다른 시스템이다#

  • 승급: 동일 유닛을 흡수해 등급과 전투 성능을 올린다.
  • 각인: 소환된 개별 유닛에 붙는 런 내부 랜덤 옵션이다.
  • 코어: 유닛이 아니라 심볼 가중치·릴 축·판정 규칙을 바꾸는 런 내부 장비다.

타이틀 화면의 한 메뉴에 셋을 합치지 않는다. 런타임 데이터와 발동 시점이 다르므로 구현도 분리한다.

확정된 요구#

HouseMetaUpgrade — 종족별 영구 메타#

현재 확정된 범위는 다음과 같다.

  • 업그레이드 진행은 HouseKey별로 독립한다.
  • 타이틀 업그레이드 화면에서 종족을 전환해 각 종족의 진행을 따로 본다.
  • 구현은 공용 데이터/공용 UI를 쓰고 종족별 프리팹·클래스를 복제하지 않는다.
  • 한 종족의 업그레이드 노드는 그 종족에만 적용한다. 다른 종족에 대한 교차 적용은 별도 노드가 명시된 경우에만 허용한다.
  • 런 내부 흡수 등급·각인·코어 보유는 이 영구 진행도에 저장하지 않는다.

아직 확정되지 않은 것은 노드 구성, 효과, 레벨 수, 재화, 비용, 획득 경로다. 따라서 이 단계에서 “체스 공격력 +5%” 같은 노드를 예시값으로도 CSV에 넣지 않는다.

UnitGrowth — 승급 단계#

런 내부 승급도 공용 흡수 규칙을 쓰되 HouseKey/UnitKey별 데이터로 분리한다. 원문이 확정한 공통 골격은 3기 흡수와 1성→2성→3성→프리즘이며, 종족 차이는 UnitTable 스탯·3성 SkillId·필요하면 별도 성장 규칙 레코드로 표현한다. 종족마다 흡수 개수나 배수를 다르게 한다는 근거는 아직 없으므로 공통값을 유지한다.

단계 조건 GDD 스탯 배수 추가 효과
1성 기본 소환 ×1.0 각인 1개 롤
2성 동일한 1성 유닛 3기 흡수 ×2.6 유지할 각인 + 1개 추가 롤
3성 동일한 2성 유닛 3기 흡수 ×7.0 종족 고유 스킬 해금
프리즘 3성 + 심판 웨이브 클리어 ×18.0 전장 2칸 점유, 각인 수치 최대 고정

동일 유닛은 구현상 같은 UnitKey를 뜻해야 한다. 등급은 재료 조건으로 따로 비교한다. 스프라이트 배열 인덱스만으로 동일성을 판정하면 리소스 순서 변경 시 다른 유닛이 합쳐질 수 있으므로 금지한다.

Imprint — 각인 풀#

키(예정) 효과 범위 가중치
Blade 공격력 증가 +12~28% 24
Thickness 체력 증가 +15~35% 24
Rhythm 공격 속도 증가 +10~22% 18
Range 사거리 증가 +1칸 12
Kinship 같은 종족 유닛 1기당 공격력 증가 +3% 10
Outsider 다른 종족 유닛 1기당 공격력 증가 +6% 8
Realign 이 유닛 소환 시 스핀 코인 획득 +1 4

영문 키는 구현 제안이며 표시명은 StringTable 키로 분리한다. 실제 CSV에는 GDD의 StatType, MinValue, MaxValue, Weight만으로 표현하기 어려운 Kinship·Outsider·Realign이 있으므로 EffectType과 TriggerType을 분리하는 편이 안전하다.

Core — 코어 경계#

코어는 승급 테이블에 넣지 않는다. 대표 확정 예시는 다음과 같다.

  • 심볼 가중치: 편중된 주형, 추방령
  • 릴 축: 고정 축, 역회전
  • 판정 규칙: 객장의 규칙, 이중 장부

코어 상점은 5~7연차에 열리고 S등급 코어는 9~11연차에 등장한다. 다만 slot-weight.html가 지적한 편중된 주형 +40%의 해석·중첩 제한과 추방령의 지속 범위가 아직 확정되지 않았으므로, 흡수 승급 프로토타입과 동시에 구현하지 않는다.

부분 구현#

  • 슬롯 UI는 3×3을 회전하고 멈출 수 있지만, 정지 결과를 게임 판정·소환 데이터로 반환하지 않는다.
  • RunData는 HP·연차·골드·스핀 코인·스왑·배속만 가진다. 유닛·웨이브·코어 상태는 없다.
  • OnBattleStart()는 전투를 시작하지 않는다. 웨이브 승리/심판 승리 이벤트도 없다.
  • PlayerManager.UnlockHouse() API는 있으나 왕 처치 후 호출 경로는 없다.
  • 현재 HouseTable.csv는 슬롯·체스·장기·화투·포커·마작 6종 모두 isUnlocked=1이다. 따라서 GDD의 종족 해금 메타는 데이터상 비활성화되어 있다.
  • 종족별 영구 메타는 HouseUpgradeTable, 읽기 전용 저장 조회, 공용 팝업과 6개 종족 탭까지 구현됐다. 승인된 노드·재화·효과가 없어 CSV는 헤더뿐이며 화면은 빈 상태를 표시한다.

완전 미구현#

  • UnitTable, ImprintTable, CoreTable
  • 판정 결과 → 소환 명령 변환
  • 전장 유닛 런타임 모델과 3×3 점유 데이터
  • 흡수/연쇄 승급
  • 각인 가중치 롤과 효과 적용
  • 전투·사망·웨이브 클리어
  • 프리즘 2칸 점유
  • 코어 획득·장착·상점
  • 종족별 메타 업그레이드의 실제 노드 행·재화·구매·효과 적용과 RunData 스냅샷

즉 현재 상태는 흡수 승급 자체가 아니라 그 입력이 되는 판정·소환·전투도 아직 없는 단계다.

데이터 스키마#

HouseUpgradeTable.csv — 종족별 메타 노드/레벨#

공용 테이블 한 장에 전 종족을 넣고 HouseKey로 분리한다. 값이 아직 정해지지 않았으므로 아래는 스키마만 확정하는 제안이다.

필드 타입 설명
Id int 레코드 Id
Key string 레벨이 바뀌어도 유지되는 안정적인 노드 키. 행 유일성은 (HouseKey, Key, Level) 조합으로 보장
HouseKey string HouseTable.Key 조인. 종족별 독립의 핵심
NameKey string 표시명 StringTable 키
DescKey string 설명 StringTable 키
Level int 같은 노드의 단계. 단일 단계면 1
EffectType enum 승인된 효과 처리기 종류
TargetKey string 적용 대상 스탯·기구 키
Value float 해당 단계의 효과값. 수치 미정
CostType string/enum 비용 종류. 재화 기획 전에는 확정 불가
CostValue int 해당 단계 비용. 수치 미정
PrerequisiteKey string 같은 종족 안의 선행 노드 Key. 선형 구조면 빈 값 가능
SortOrder int 종족 화면 내 표시 순서
IconPath string 아이콘 리소스 경로

레벨마다 한 행을 두면 비용 곡선 공식을 새로 만들 필요가 없고, 종족별로 레벨 수가 달라도 같은 로더를 쓸 수 있다. 트리형인지 선형인지 결정되지 않았으므로 좌표 컬럼은 아직 넣지 않는다. 트리형을 채택할 때만 UI 위치 데이터를 추가한다.

PlayerData — 종족별 영구 진행 저장#

Unity JsonUtility는 일반 Dictionary 직렬화에 맞지 않으므로 직렬화 가능한 리스트를 쓴다.

HouseUpgradeProgressData
  houseKey: string
  listNodeProgress: List<HouseUpgradeNodeProgressData>

HouseUpgradeNodeProgressData
  nodeKey: string
  level: int

PlayerData에는 List<HouseUpgradeProgressData> 한 필드만 추가하고, 밖에서는 PlayerManager의 API로만 변경한다. 기존 SaveData.SetChanged() 경로를 유지해야 자동 저장이 빠지지 않는다.

읽기 API는 구현됐고, 나머지는 재화·구매 계약 확정 뒤의 예정 API다.

int GetHouseUpgradeLevel(houseKey, nodeKey)
bool CanPurchaseHouseUpgrade(houseKey, nodeKey)
bool TryPurchaseHouseUpgrade(houseKey, nodeKey)
IReadOnlyList<HouseUpgradeRecord> GetHouseUpgradeRecords(houseKey)

TryPurchase는 재화·선행 조건이 확정된 뒤 구현한다. 지금은 빈 재화를 가정해 성공시키는 임시 코드를 만들지 않는다.

런 시작 시 메타 효과 스냅샷#

영구 메타를 매 프레임 PlayerData에서 직접 읽지 않는다. 선택 종족으로 런을 시작할 때 해당 HouseKey 진행을 HouseUpgradeModifierSet으로 계산해 RunData에 스냅샷한다.

  • 저장 데이터 변경 경로와 전투 계산 경로를 분리한다.
  • 런 도중 타이틀 저장값이 바뀌어도 진행 중 런의 밸런스가 갑자기 변하지 않는다.
  • 메타 0 기준 QA에서는 빈 modifier set을 주입해 GDD 프로토타입 기준을 유지할 수 있다.

효과 적용 순서(등급 배수 전/후, 각인 전/후)는 실제 노드 효과가 정해진 뒤 확정한다. 지금 순서를 만들면 수치 설계를 선점하게 된다.

UnitTable.csv — 유닛 등급별 확정 스탯#

GDD 초안은 Id, SymbolId, Grade, Hp, Atk, AtkSpeed, Range, TargetType, SkillId를 제안한다. 현재 프로젝트는 문자열 키 조인을 주로 쓰므로 다음 형태를 권장한다.

필드 타입 설명
Id int 레코드 Id
Key string {HouseKey}_{SymbolKey}_{Grade} 형태의 유일 키
UnitKey string 등급이 달라도 같은 유닛임을 판정하는 키
HouseKey string 종족 조인 키
SymbolKey string 심볼 조인 키
Grade enum/int OneStar, TwoStar, ThreeStar, Prism
Hp float 해당 등급의 최종 기본 체력
Atk float 해당 등급의 최종 기본 공격력
AtkSpeed float 해당 등급의 최종 기본 공격 속도
Range int 해당 등급의 기본 사거리
TargetType enum 대상 선택 규칙
SkillId string 3성 고유 스킬 등. 없으면 빈 문자열
OccupyCount int 프리즘 2, 나머지 1

GDD에 Grade별 행과 스탯 배수가 동시에 적혀 있으므로 이중 적용을 막아야 한다. 권장 해석은 다음과 같다.

  • 런타임은 UnitTable의 등급별 최종 스탯을 그대로 사용한다.
  • ×1.0 / ×2.6 / ×7.0 / ×18.0은 데이터 작성·검증 기준으로 사용한다.
  • 검증기가 1성 대비 등급 행의 배수를 검사하되 런타임에서 다시 곱하지 않는다.

원문 ~152행은 당시 38심볼 × 4등급 초안이다. 현재 프로젝트는 슬롯·마작이 추가되어 심볼 수가 늘었으므로 행 수를 152로 고정하지 않는다.

RunData 확장 방향#

RunData 자체에 모든 로직을 몰아넣지 않고 상태만 소유한다.

  • listUnit: 현재 런의 유닛 로스터/전장 상태
  • listCoreKey: 현재 런에서 획득한 코어
  • clearedJudgmentYear: 프리즘 조건 판정용 심판 클리어 기록
  • 필요 시 nextRuntimeUnitId

변경 로직은 UnitGrowthSystem, 전장 점유는 BattlefieldState, 각인 롤은 ImprintRoller처럼 분리한다. 클래스명은 구현 제안이며 기획 수치를 추가하지 않는다.

트리거 시점과 데이터 흐름#

A. 타이틀 종족별 메타#

TitleScene.OnClickUpgradeButton()
  -> UIManager.Get<UIHouseUpgrade>()
  -> HouseTable에서 표시할 종족 목록 조회
  -> 기본 탭 = PlayerManager.GetSelectedHouseRecord().Key
  -> HouseUpgradeTable.GetListByHouseKey(houseKey)
  -> PlayerManager의 해당 houseKey 진행도와 합쳐 표시
  -> 구매/해금 요청
  -> 비용·선행 조건 검증
  -> PlayerData의 해당 houseKey/nodeKey level만 변경
  -> SaveData.SetChanged()
  -> 현재 종족 화면 새로고침

다른 종족 탭으로 이동해도 selectedHouseKey를 자동 변경하지 않는다. 플레이 종족 선택과 업그레이드 열람은 서로 다른 의도이기 때문이다.

인게임 진입 시:

TitleScene.OnClickPlayButton()
  -> 선택 종족 HouseKey 확정
  -> 해당 종족의 HouseUpgradeModifierSet 계산
  -> RunData.Init(modifierSet)

현재 SceneManager.NextScene()은 런 인자를 전달하지 않으므로, 실제 구현에서는 InGameScene.OnSetup()이 PlayerManager.GetSelectedHouseRecord()로 fallback까지 적용된 종족을 확정한 뒤 modifier set을 만들 수 있다. raw selectedHouseKey는 첫 실행에 빈 문자열일 수 있으므로 직접 사용하지 않는다. 장기적으로 런 부팅 객체가 생기면 그쪽으로 옮긴다.

B. 런 내부 승급#

InGameScene.CoSpinAndStop()
  -> UIHouseSlotMachine 정지 결과 3×3 반환
  -> JudgeSystem 판정
  -> SummonBatch 생성
  -> RunData/BattlefieldState에 유닛 추가
  -> UnitGrowthSystem에서 흡수 가능 상태 계산
  -> 승급 처리
  -> 배치 단계 활성화
  -> InGameScene.OnBattleStart()
  -> 전투
  -> WaveCleared 이벤트
  -> 심판 웨이브라면 Prism 승급 가능 상태 갱신
  -> 다음 연차

일반 승급#

GDD의 코어 루프는 판정 → 배치 → 전투 순서다. 따라서 새로 소환된 유닛을 포함한 흡수 승급 판정은 판정 결과가 전장 상태에 반영된 직후, 배치 조작을 열기 전이 가장 자연스럽다. 다만 자동 승급인지 플레이어 선택인지 원문에 없으므로 실제 실행은 U-2 결정에 따른다.

프리즘#

향후 전투 시스템이 WaveCleared(WaveRecord)를 발행하고, WaveType == Judgment일 때 프리즘 조건을 갱신한다. 현재는 전투와 WaveTable 자체가 없으므로 InGameScene.OnBattleStart()에 프리즘 로직을 임시로 넣지 않는다. 임시 훅은 나중에 두 번째 갱신 경로가 되어 제거를 놓치기 쉽다.

각인#

  • 1성 유닛 생성 직후 가중치로 1개 롤한다.
  • 2성 생성 시 유지 대상으로 확정된 각인을 복사한 뒤 1개를 추가 롤한다.
  • 3성은 GDD에 추가 롤 문구가 없으므로 새 각인을 롤하지 않는다.
  • 프리즘은 보유 각인의 값을 해당 레코드의 최대값으로 고정한다.

Realign은 소환 시 스핀 코인 +1이므로 승급으로 새 런타임 유닛이 만들어졌다고 다시 발동시키면 안 된다. 실제 스핀 판정이 새 1성 유닛을 소환한 시점에만 OnSummon을 발행해야 한다. 다만 2성 추가 롤에서 Realign이 나오면 즉시 발동하는지 여부는 U-6이다.

공식 / 로직#

흡수 가능 조건#

CanAbsorb(a, b, c) =
  a.unitKey == b.unitKey == c.unitKey
  && a.grade == b.grade == c.grade
  && grade in {OneStar, TwoStar}
  • 1성 3기 → 2성 1기
  • 2성 3기 → 3성 1기
  • 3성은 3기 흡수 규칙이 아니라 심판 웨이브 클리어 조건으로 프리즘이 된다.

연쇄 승급#

한 소환 배치에서 1성 9기가 모이면 1성 9 → 2성 3 → 3성 1 연쇄가 가능하다. 자동 승급을 채택하면 한 번만 검사하지 말고 더 이상 승급할 수 없을 때까지 반복한다.

repeat
  candidate = FindNextAbsorbCandidate()
  if candidate 없음: break
  Absorb(candidate)
until false

결정성 확보를 위해 후보 선택 순서는 grade 낮은 순 → unitKey → runtimeId 같은 고정 규칙을 써야 한다. 어떤 각인을 남길지는 기획 결정이므로 U-3이 닫히기 전에는 흡수 결과를 확정할 수 없다.

스탯#

권장 런타임 공식은 다음과 같다.

FinalStat = UnitTable[unitKey, grade].BaseStat
FinalStat *= 각인 배율들의 합성 결과
FinalStat *= 동향/이방인처럼 현재 전장 구성에 따른 동적 배율

등급 배수는 이미 UnitTable 등급 행에 반영하고 다시 곱하지 않는다. 각인 여러 개의 합성 방식(합연산/곱연산)은 GDD에 없으므로 U-5로 남긴다.

각인 가중치 롤#

totalWeight = Σ enabledImprint.Weight
roll in [0, totalWeight)
누적 가중치가 roll을 처음 넘는 행을 선택
value = Random.Range(MinValue, MaxValue)

프리즘은 value = MaxValue. Range +1, Kinship +3%, Outsider +6%, Realign +1은 Min/Max를 같은 값으로 둔다.

단계별 구현 구상#

Phase 0 — 선행 기반: 판정 결과와 소환 데이터#

  1. UIHouseSlotMachine이 최종 3×3 심볼 키/인덱스를 반환한다.
  2. UI와 분리된 JudgeSystem이 소환 명령 목록을 만든다.
  3. UnitTable과 전장 3×3 점유 상태를 만든다.
  4. InGameScene을 스핀 → 판정 → 배치 → 전투 상태 흐름으로 나눈다.

이 단계가 없으면 승급할 유닛 자체가 없으므로 Upgrade UI부터 만드는 순서는 맞지 않는다.

Phase 1 — 체스 흡수 승급 MVP#

GDD §12 순서를 따른다.

  1. 체스 유닛만 1성/2성/3성 데이터 작성
  2. 동일 3기 흡수와 연쇄 승급 구현
  3. 등급 배수와 3성 고유 스킬 슬롯 연결
  4. 전장에 별 등급 표시와 흡수 연출 추가
  5. 오토배틀과 함께 12연차 완주 검증

이 단계에서는 코어를 넣지 않는다. GDD 프로토타입 순서상 각인도 뒤 단계이므로, 승급 구조 검증을 막지 않도록 각인 슬롯은 비워 둔다.

Phase 2 — 각인#

  1. ImprintTable 7행과 가중치 롤
  2. 1성 소환 롤
  3. 2성 승급 시 유지/추가 롤
  4. 상시·전장 구성 의존·소환 트리거 효과 분리
  5. 각인 아이콘/툴팁과 프리즘 최대값 표시

U-3·U-5·U-6이 닫혀야 완료할 수 있다.

Phase 3 — 심판과 프리즘#

  1. WaveTable / 전투 결과 / 심판 클리어 이벤트
  2. 프리즘 승급 대상 선택
  3. 2칸 점유 규칙과 배치 가능성 검사
  4. 각인 최대값 고정
  5. 8연차부터 실제 도달 가능성 검증

프리즘은 전장 점유 규칙이 먼저 없으면 구현할 수 없다.

Phase 4 — 코어#

  1. CoreTable과 런 보유 목록
  2. 5~7연차 코어 상점
  3. 가중치 → 릴 축 → 판정 규칙 순서로 효과 계통 구현
  4. 9~11연차 S등급 등장
  5. slot-weight.html의 미결정 코어 수치·중첩·지속 범위 승인 후 밸런스 검증

Phase M — 종족별 영구 메타#

이 단계는 런 승급 Phase 0~4와 독립된 작업 레인이다. 다만 GDD의 최소 재미 검증을 먼저 지키려면 Phase 1 체스 흡수 MVP 뒤에 활성화하는 편이 안전하다.

  1. HouseUpgradeTable/Record/Table과 GetListByHouseKey() 추가
  2. PlayerData에 종족별 진행 리스트, PlayerManager에 조회·변경 API 추가
  3. UIHouseUpgrade 공용 팝업 제작
  4. UITable.csv에 UIHouseUpgrade,Popup,... 등록
  5. TitleScene.OnClickUpgradeButton()에서 UIManager.Get<UIHouseUpgrade>()
  6. 런 시작 시 선택 종족의 modifier set 스냅샷
  7. 메타 0/적용 두 QA 프로필로 클리어율 비교

노드 효과·비용이 미정인 상태에서 1~5의 골격과 읽기 전용 화면까지는 만들 수 있지만, 실제 구매와 전투 효과 적용은 M-2~M-5가 닫힌 뒤 진행한다.

인게임 승급 표시#

  • 유닛마다 1성/2성/3성/프리즘을 즉시 구분할 표식
  • 흡수 재료 3기와 결과 1기의 관계를 보여주는 짧은 연출
  • 자동 승급이면 발생 전후에 전장 점유가 어떻게 바뀌었는지 표시
  • 프리즘은 2칸 점유를 승급 확정 전에 미리 보여주고, 공간 부족 시 이유를 표시
  • 각인은 아이콘 + 실제 롤 값, 프리즘은 최대값임을 별도 표현

32px 픽셀 아트와 모바일 가로 화면을 전제로 긴 문장 대신 아이콘·숫자를 우선한다. 구체 좌표와 크기는 전장 UI 설계가 아직 없어 이 문서에서 만들지 않는다.

타이틀 메뉴#

타이틀의 업그레이드 버튼은 종족별 영구 메타 화면으로 연결한다는 가정이다. 런 유닛 흡수 승급을 직접 수행하게 해서는 안 된다. 런 유닛은 타이틀에 존재하지 않고 저장도 하지 않기 때문이다.

UIHouseUpgrade는 공용 팝업 하나로 구성한다.

  • 상단/좌측 종족 선택: HouseTable 순서와 해금 상태 재사용
  • 기본 종족: PlayerManager.GetSelectedHouseRecord().Key로 확정한 현재 종족
  • 본문: 해당 HouseKey의 노드/단계만 표시
  • 진행도: 종족별 구매/해금 수, 필요하면 다음 단계 조건
  • 하단: 비용과 적용 효과. 값이 확정되기 전에는 구매 버튼을 노출하지 않음

종족마다 전용 프리팹을 여섯 개 만들지 않는다. 종족별 차이는 테이블 행, 액센트 색, 아이콘, 설명으로 표현한다. 특수한 레이아웃이 실제로 필요한 종족만 후속 확장 포인트를 둔다.

엣지 케이스#

  • 같은 nodeKey가 두 종족에 중복되거나 잘못된 HouseKey로 저장됨
  • 테이블에서 노드가 삭제/이름 변경됐지만 기존 저장에 진행이 남음
  • 잠긴 종족의 메타 화면 열람·구매 허용 여부
  • 최대 레벨 노드를 다시 구매함
  • 선행 노드가 충족되지 않았는데 저장에는 후속 노드가 열려 있음
  • 재화 차감과 진행 저장 사이에 앱이 종료됨
  • 메타 업그레이드 구매 직후 진행 중 런에도 소급 적용되는 문제
  • 다른 종족 탭을 보다가 플레이 종족이 의도치 않게 변경됨
  • 혼혈 유닛이 두 종족의 메타 보너스를 중복 적용받음
  • 한 배치에서 여러 흡수 후보가 동시에 생김
  • 1성 9기처럼 연쇄 승급이 생김
  • 재료 유닛마다 서로 다른 각인을 보유함
  • 흡수 재료가 서로 다른 현재 HP를 가짐
  • 승급 결과가 기존 셀을 유지할지 새 셀을 선택할지
  • 전장이 가득 찬 상태에서 흡수로 공간이 생김
  • 프리즘 2칸을 놓을 연속 공간이 없음
  • 여러 3성이 심판 웨이브를 동시에 클리어함
  • 프리즘 승급 뒤 2칸 중 한 칸만 유효해지는 배치/스왑
  • 프리즘의 죽음 또는 이동 시 2칸 점유 해제
  • 승급 중 OnSummon 각인이 중복 발동함
  • 가중치가 0이거나 전체 합이 0인 각인 테이블
  • 동일 각인 중복 허용 여부
  • 런 종료·씬 전환 때 런 데이터가 남음
  • 유닛 사망을 영구 소멸로 할지 연차 종료 부활로 할지에 따라 흡수 재료 풀이 달라짐

문서에 없어서 확인이 필요한 부분#

U-1. “종족마다 업그레이드”의 저장 범위 — 결정됨 (2026-08-28) · 영구 메타#

타이틀 UpgradeButton에서 종족별 노드를 해금하고 그 진행은 다음 런에도 유지한다. 사용자 확인으로 영구 메타 진행이 확정됐으며, 기존 GDD §09의 “초기 빌드 영구 강화 트리 제외” 제한은 최신 결정에 맞춰 개정 대상이 된다.

영구 메타와 런 내부 성장은 이름·데이터·UI에서 계속 분리한다. 영구 노드가 런의 유닛 등급이나 각인·코어 보유 상태를 직접 저장하는 식으로 합치지 않는다.

M-2. 종족별 메타의 형태 — 구현 전 필수#

  • 선형 단계 목록
  • 선행 노드가 있는 트리
  • 선택지 중 하나만 고르는 분기

형태에 따라 UI 레이아웃과 초기화/재분배 규칙이 달라진다. 현재 스키마는 선형과 선행 노드를 모두 담을 수 있지만, 화면 좌표는 트리형 확정 전까지 넣지 않는다.

M-3. 영구 재화와 획득 경로 — 구현 전 필수#

재화명, 단일 공용 재화인지 종족별 재화인지, 런 종료/왕 처치/업적 중 어디서 얻는지, 패배 시에도 얻는지가 전부 미기재다. eCurrencyType은 현재 None/Max뿐이며 임의 값을 추가하지 않는다.

M-4. 종족별 실제 노드 효과와 수치 — 구현 전 필수#

“종족마다 따로”라는 구조만 확정됐고 각 종족의 정체성을 강화할 노드 목록은 없다. 최소한 종족별로 다음을 작성해야 한다.

  • 노드 이름/설명
  • 대상 시스템과 EffectType
  • 레벨 수
  • 단계별 값
  • 선행 조건
  • 비용

공격력 같은 공용 스탯만 여섯 번 복제하면 종족별 분리의 의미가 약해진다. 반대로 판정 확률·홀드·배팅처럼 종족 고유 기구를 영구 강화하면 GDD의 종족 밸런스를 직접 바꾸므로 시뮬레이션이 필요하다.

M-5. 초기화·재분배·최대 진행#

  • 구매 취소/재분배 가능 여부와 비용
  • 종족 하나를 완주하는 데 필요한 런 수
  • 종족별 최대 레벨 차이를 허용할지
  • 새 종족 추가 시 기존 저장의 기본값

M-6. 혼혈 유닛에 어떤 종족 메타를 적용하는가#

전리품으로 다른 종족 심볼/유닛이 들어왔을 때 다음 중 어느 진행을 쓰는지 미기재다.

  • 유닛 원래 HouseKey의 메타 진행
  • 현재 플레이 종족의 메타 진행
  • 영구 메타 미적용

첫 번째는 여러 종족을 키운 계정이 혼혈에서 더 강해지고, 두 번째는 선택 종족 빌드로 단순화되며, 세 번째는 순혈 보상으로 작동한다. 핵심 밸런스 결정이므로 구현에서 추측하지 않는다.

U-2. 흡수 승급이 자동인가, 플레이어 선택인가 — 구현 전 필수#

  • 자동: 템포가 빠르고 프로토타입에 적합하지만 어떤 각인·셀을 남길지 규칙이 필요하다.
  • 선택: 빌드 판단이 생기지만 GDD §02가 플레이어 결정 지점을 스핀 재굴림과 외교 두 곳으로 압축한 방향과 충돌할 수 있다.

U-3. 흡수 시 어느 각인을 유지하는가 — 각인 구현 전 필수#

각인 유지 + 1개 추가 롤은 적혀 있지만 재료 3기가 각기 다른 각인을 가질 때의 병합 규칙이 없다.

  • 대표 유닛 1기의 각인만 유지
  • 셋 중 하나를 플레이어가 선택
  • 세 유닛 각인을 모두 합침

세 번째는 등급이 오를수록 각인 수가 폭증하므로 원문 문구와 맞지 않을 가능성이 높지만, 최종 선택은 기획 결정이다.

U-4. 프리즘 승급 대상과 횟수#

  • 심판 웨이브를 클리어한 모든 3성이 자동 프리즘인지
  • 3성 하나를 선택하는지
  • 4·8·12연차마다 가능한지, GDD 표의 8연차 프리즘 가능 시점 이후만 가능한지
  • 런당 프리즘 수 제한이 있는지

3성 + 심판 웨이브 클리어와 8연차부터 가능만 확정돼 있다.

U-5. 등급 배수와 각인 합성 범위#

  • ×2.6/×7.0/×18.0이 HP·ATK만인지 공격 속도·사거리까지 포함하는지
  • 동일 스탯 각인 여러 개가 합연산인지 곱연산인지
  • Kinship/Outsider가 살아 있는 전장 유닛만 세는지 런 로스터 전체를 세는지

U-6. 2성 추가 롤에서 Realign이 나오면 즉시 발동하는가#

원문은 이 유닛 소환 시라고만 쓴다. 승급은 소환이 아니므로 기본 구현 해석은 발동하지 않음이지만, 그러면 2성 추가 롤로 얻은 Realign은 이후 새로 소환되는 유닛이 아니어서 영원히 발동하지 않을 수 있다. 효과 문구 또는 승급 트리거를 확정해야 한다.

U-7. 유닛 사망 처리#

GDD §14의 기존 미결정이다: 영구 소멸 / 연차 종료 시 부활. 흡수 재료 보존과 12연차 성장 곡선에 직접 영향을 주므로 오토배틀 MVP 전에 닫아야 한다.

U-8. 승급 후 위치와 현재 HP#

  • 재료 셋 중 어느 셀을 결과가 차지하는지
  • 현재 HP를 전부 회복하는지, 비율 유지인지, 합산인지

전투 중 승급하지 않고 판정·배치 단계에서만 승급하게 하면 HP 문제는 줄지만, 연차 간 생존 규칙 U-7은 여전히 필요하다.

U-9. 종족 고유 3성 스킬#

3성에서 종족 고유 스킬을 해금한다고만 되어 있고 스킬 목록·효과·수치는 없다. SkillId 자리만 만들고 빈 값으로 출고할 수 있지만, 3성 완성 검증에는 최소 체스 스킬 하나가 필요하다.

구현 승인 게이트#

  1. 종족별 메타 골격: U-1 영구 메타가 확정됐으므로 HouseUpgradeTable/저장 모델/읽기 전용 UIHouseUpgrade 골격까지 진행 가능하다.
  2. 메타 구매·효과 적용 전 필요: M-2(형태), M-3(재화/획득), M-4(노드/수치), M-5(재분배), M-6(혼혈 적용).
  3. 런 승급 지금 진행 가능: Phase 0 구조 설계, UnitTable/런타임 모델 골격, 체스 1~3성 흡수 프로토타입. 단 U-2/U-3/U-7/U-8을 먼저 결정해야 실제 결과 규칙을 고정할 수 있다.
  4. 각인 전 필요: U-3/U-5/U-6.
  5. 프리즘 전 필요: U-4/U-7/U-8 및 전장 2칸 점유 설계.
  6. 코어 전 필요: slot-weight.html §10-3/§10-4와 추방령 지속 범위.
