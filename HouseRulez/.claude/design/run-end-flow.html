런 종료 / 전투 종료 후 흐름

전투 결과(UIInGameBattle.result)가 런 상태(RunData)로 흘러가고, 본거지가 무너지거나 최종 연차를 완주했을 때 런을 닫아 옥새를 지급하기까지의 구현 스펙이다. GDD가 이 구간을 비워뒀으므로 기존 코드에서 확정할 수 있는 것과 사용자 결정이 필요한 것을 엄격히 분리했다.

2. 개요 — 지금 무엇이 비어 있나

전투 결과 파이프라인은 양 끝만 있고 가운데가 없다. 아래는 코드로 확인한 사실이다.

[공급]  UIInGameBattle.CheckResult()        → m_Result = Victory / Defeat
        UIInGameBattle.CheckHomeLine()      → m_HomeHit++
              │  public eBattleResult result / int homeHit / bool isRunning
              ▼
        ╔═══════════════════════════════════════════════════════╗
        ║   ★ 비어 있는 구간 — 이 문서가 채우는 곳               ║
        ║   ① 전투 종료 프레임 감지                             ║
        ║   ② 웨이브 정산(본거지 피해 / 웨이브 진행)            ║
        ║   ③ 연차 전환(스핀 코인·스왑 리셋, 외교 진입 자리)    ║
        ║   ④ 런 종료 판정 → 옥새 지급 → 결과 화면              ║
        ╚═══════════════════════════════════════════════════════╝
              │
              ▼
[소비]  RunData.AdvanceWave()      호출부 0곳
        RunData.TakeHomeDamage()   호출부 0곳
        RunData.GetRoyalReward()   호출부 0곳
        PlayerManager.AddRoyal()   호출부 0곳  ← 옥새를 버는 경로가 게임 전체에 없다
        PlayerManager.UnlockHouse() 호출부 0곳

옥새 획득 경로가 0곳이라는 건 곧 UIHouseUpgrade(종족 업그레이드 트리)가 현재 영원히 구매 불가라는 뜻이다. 런 종료를 붙이는 것이 그 화면을 살리는 유일한 통로다.

단계 구분 — 무엇이 이 문서 밖인가

단계내용소유
1단계전투 종료 프레임 감지 · 승리→AdvanceWave() / 패배→TakeHomeDamage() · HUD 갱신 · 중앙 배너 결과 한 줄 · 스핀/전투 버튼 연타 가드호출자(이미 진행 중)
2단계연차 전환 · 런 종료 판정 · 옥새 지급 · 결과 팝업 · 재시작/타이틀이 문서
3단계외교(DiplomacyTable) · 침공 예고(SIDE 영역) · 상점이 문서는 훅 자리만 정하고 구현은 별도

1단계와 2단계는 같은 메서드(OnBattleFinished())를 건드린다. §5의 의사코드는 1단계 몫까지 포함한 완성형이므로, 1단계가 이미 붙어 있으면 그 위에 덧붙이는 형태로 읽으면 된다.

3. 먼저 알아야 할 실측 결함 4건

결정을 내리기 전에 알아야 한다. 넷 다 코드를 읽어 확인한 것이고, D2·D3는 1단계 설계를 그대로 두면 런이 영원히 끝나지 않게 만든다.

D1 — 씬이 열린 첫 프레임에 result가 이미 Victory가 된다

UIInGameBattle.m_Result의 초기값이 Running이라 isRunning이 참이고, InGameScene.Update()(190행)가 첫 프레임부터 Tick()을 부른다. 유닛 목록이 비어 있으므로 CheckResult()(294행)가 anyEnemy == false로 판단해 즉시 Victory를 세운다.

결과 — "isRunning이 참→거짓으로 바뀐 프레임"을 종료로 잡으면 스핀 한 번 하기 전에 1웨이브 승리가 정산된다. 반드시 "전투가 실제로 시작된 적 있다" 플래그로 게이트해야 한다(§5의 m_isBattleStarted).

D2 — 패배해도 본거지가 안 깎인다

m_HomeHit은 본거지 선을 넘은 적의 마릿수다. 그런데 패배 판정(아군 전멸)이 나는 순간 Tick()이 멈추므로, 남은 적은 본거지까지 걸어가지 못하고 그 자리에 선다. 즉 패배 시 homeHit은 대체로 0이다(전투 중 한 레인이 비어 적이 미리 새어 나간 경우에만 0보다 크다).

결과 — 1단계의 "패배 → TakeHomeDamage(homeHit)"는 대부분 TakeHomeDamage(0)이 되고, TakeHomeDamage()는 _amount <= 0이면 그대로 반환한다(137행). 본거지 HP가 절대 줄지 않아 런이 끝날 방법이 없다. 패배 자체에 대한 고정 피해가 별도로 필요하다 → §8 Q3.

D3 — 같은 병력으로 무한 재전투가 된다

m_LastJudgeResult/m_LastGrid(InGameScene 292행 부근에서 설정)는 전투가 끝나도 비워지지 않는다. OnBattleStart()(142행)는 이 값이 null이 아니기만 하면 m_Battle.Begin()을 다시 부르고, Begin()은 Clear()로 결과를 Running으로 되돌린다.

결과 — 전투 시작 버튼을 다시 누르면 스핀 코인 소모 없이 같은 병력으로 처음부터 다시 싸운다. 패배가 사실상 무의미해진다. 전투 종료 처리에서 두 필드를 반드시 null로 비운다.

D4 — 2연차에 들어가는 순간 진행이 막힌다

spinCoinMax = 3(SpinCoinPerYear), WAVE_PER_YEAR = 3. 스핀 1회 = 코인 1개 = 웨이브 1개이므로 1연차 세 웨이브를 마치면 코인이 0이다. 그런데 AdvanceWave()(126행)는 코인·스왑을 회복하지 않는다(주석에 TODO로만 남아 있음).

결과 — 2연차 진입 직후 SpendSpinCoin()이 false를 돌려 스핀이 안 된다. D3와 겹치면 "스핀은 못 하는데 1연차의 마지막 병력으로 2연차 전투는 계속 걸 수 있는" 상태가 된다. 연차 전환 리셋은 이 문서의 필수 항목이며, GDD §03("연차 시작 시 지급, 이월 없음")에 근거가 있으므로 창작이 아니다.

4. 트리거 시점

이벤트와 훅 지점 — 전부 InGameScene이 소유한다(RunData의 유일한 변경 통로이기 때문)
이벤트정확한 훅판정식
전투 종료 InGameScene.Update() 190행 — m_Battle.Tick() 직후 m_isBattleStarted == true && m_Battle.isRunning == false
D1 때문에 isRunning 단독으로는 못 쓴다
웨이브 진행 새 메서드 InGameScene.OnBattleFinished() 안에서 m_RunData.AdvanceWave() §8 Q3의 결정에 따름
연차 전환 RunData.AdvanceWave() 126행 내부 — m_WaveIndex가 1로 되돌고 m_Year++ 하는 분기
해당 메서드의 기존 TODO 주석이 이 자리를 지목한다		 m_WaveIndex > WAVE_PER_YEAR
런 종료(본거지 함락) OnBattleFinished() — 본거지 피해 반영 직후 m_RunData.homeHp <= 0
런 종료(완주) OnBattleFinished() — AdvanceWave() 이전 year >= yearMax && waveIndex >= WAVE_PER_YEAR
= WaveTable.csv의 WaveType == Final인 36행
외교 단계 자리만 연차 전환 훅 직후, 다음 연차 첫 스핀 이전 GDD §09 "3연차부터 외교 개방" → year >= 3. 구현은 이 문서 밖
왜 완주 판정이 AdvanceWave() 이전인가 — 12연차 3웨이브를 이긴 뒤 AdvanceWave()를 부르면 year가 13이 된다. 그러면 결과 화면이 "도달 연차 13/12"가 되고, GetRoyalReward()가 13 × RoyalPerYear로 계산해 옥새가 1 더 나온다(18 → 19). 마지막 웨이브 승리는 AdvanceWave()를 부르지 않고 곧장 완주로 분기한다. 보상 수치에 영향 이 판단은 구현 디테일에서 나왔지만 지급량을 1 바꾸므로 §8 Q2에 확인 항목으로 올려 뒀다.

// [신설] 전투 종료 1회
private void OnBattleFinished()
{
    eBattleResult result = m_Battle.result;
    int leakCount = m_Battle.homeHit;

    // 이 판정 결과는 소진됐다. 안 비우면 같은 병력으로 다시 전투를 걸 수 있다.
    m_LastJudgeResult = null;
    m_LastGrid = null;

    GameConfigTable configTable = TableManager.instance.GetTable<GameConfigTable>();
    int homeDamage = leakCount * configTable.GetValue(GameConfigTable.KEY_HOME_DAMAGE_PER_LEAK, 1);
    if (result == eBattleResult.Defeat)
        homeDamage += configTable.GetValue(GameConfigTable.KEY_HOME_DAMAGE_PER_DEFEAT, 1);

    m_RunData.TakeHomeDamage(homeDamage);

    ShowBattleResultBanner(result);

    if (m_Hud != null)
        m_Hud.Refresh();

    if (m_RunData.homeHp <= 0)
    {
        EndRun(eRunEndReason.HomeFallen);
        return;
    }

    bool isFinalWave = (m_RunData.year >= m_RunData.yearMax
        && m_RunData.waveIndex >= RunData.WAVE_PER_YEAR);

    if (isFinalWave == true)
    {
        // 최종 웨이브는 넘어갈 다음 웨이브가 없다 — 승패와 무관하게 런이 닫힌다.
        EndRun((result == eBattleResult.Victory) ? eRunEndReason.Cleared : eRunEndReason.FinalDefeat);
        return;
    }

    AdvanceToNextWave(result);
}

// [신설] 웨이브·연차 진행
private void AdvanceToNextWave(eBattleResult _result)
{
    // ★ Q3-A(패배도 진행) 채택 시 이 조건문 자체가 없어진다
    if (_result == eBattleResult.Defeat && ADVANCE_ON_DEFEAT == false)
        return;

    bool isYearAdvanced = m_RunData.AdvanceWave();   // 반환값 신설(아래 5.3)
    if (isYearAdvanced == false)
        return;

    OnYearAdvanced();
}

// [신설] 연차가 넘어간 프레임
private void OnYearAdvanced()
{
    if (m_Action != null)
        m_Action.Refresh();

    if (m_Hud != null)
        m_Hud.Refresh();

    ShowYearStartBanner(m_RunData.year);

    // ▼ 외교 단계는 여기에 들어온다(GDD §02 STEP 05 / §09 "3연차부터 외교 개방").
    //   이 문서는 자리만 정하고 구현은 별도 작업이다.
}

// [신설] 런 종료 — 멱등
private void EndRun(eRunEndReason _reason)
{
    if (m_isRunEnded == true)
        return;

    m_isRunEnded = true;

    int royal = m_RunData.GetRoyalReward();
    PlayerManager.instance.AddRoyal(royal);
    // 명시적 Save()는 부르지 않는다 — PlayerData.AddRoyal()이 SetChanged()를 세우고
    // PlayerManager.Update()의 더티 검사가 저장한다. PlayerManager는 MonoSingleton이라
    // 씬 전환에도 살아남는다. Save()는 앱이 내려가는 시점 전용이라고 주석에 못 박혀 있다.

    UIRunResult popup = UIManager.instance.Get<UIRunResult>();
    if (popup == null)
    {
        Logger.Error("[InGameScene] EndRun Failed! UIRunResult 생성 실패 (기대: UITable.csv에 행 + Resources/Prefabs/UI/UIRunResult)");
        return;
    }

    popup.Apply(_reason, m_RunData.year, m_RunData.yearMax, royal);
}

5.3 RunData — 변경/신설

// [수정] 126행 AdvanceWave() — 반환값 신설 + 연차 자원 리셋
//   반환값: 연차가 넘어갔는가. 호출부가 0곳이라 시그니처 변경이 안전하다.
//   리셋을 여기 두는 이유: m_SpinCoin/m_SwapCount 가 private 이고,
//   기존 TODO 주석이 정확히 이 자리를 지목한다.
public bool AdvanceWave()
{
    m_WaveIndex++;
    if (m_WaveIndex <= WAVE_PER_YEAR)
        return false;

    m_WaveIndex = 1;
    m_Year++;

    // GDD §03 "연차 시작 시 지급, 이월 없음" — 더하지 않고 최대치로 되돌린다.
    m_SpinCoin = m_SpinCoinMax;
    m_SwapCount = m_SwapCountMax;

    return true;
}

m_SwapCount는 아직 소모하는 코드가 없다(스왑 단계 미구현). 그래도 같은 자리에서 함께 리셋해 두는 편이 낫다 — 스왑이 붙은 뒤 여기를 다시 찾아 고쳐야 하는 일을 없앤다.

5.4 옥새 계산 — 기존 식을 그대로 쓴다

RunData.GetRoyalReward()(149행)는 이미 완성되어 있다. 새 계산식을 만들지 않는다.

reward = year × RoyalPerYear                       (= year × 1)
       + (year >= yearMax ? RoyalClearBonus : 0)   (= +6)

예) 4연차 2웨이브에서 함락  → 4 × 1        = 4
    12연차 최종 웨이브 승리 → 12 × 1 + 6   = 18
주의 — 이 식은 "완주"를 year >= yearMax로만 판단한다. 즉 12연차에서 최종 웨이브를 지고 끝나도 완주 보너스 6이 붙는다. 의도한 것인지 확인이 필요하다 → §8 Q2.

8. 문서에 없어서 확인이 필요한 부분

전부 GDD에 서술이 없는 항목이다. 수치와 규칙은 지어내지 않았다. 각 항목에 권장안을 달았지만 결정은 사용자 몫이다.

Q1. 본거지 HP가 0이 되면 무엇이 뜨는가

선택지얻는 것잃는 것
A. 결과 팝업(UIRunResult) 권장도달 연차·획득 옥새를 보여줄 자리가 생긴다. 옥새가 화면에 안 보이면 플레이어가 영구 성장을 배울 기회가 없다. 기존 팝업 3종과 완전히 같은 패턴이라 신규 자산은 프리팹 1 + 클래스 1프리팹 제작 필요. UITable·StringTable 행 추가
B. 배너 한 줄 후 자동 타이틀 복귀신규 자산 0개. 오늘 안에 붙는다옥새 지급이 화면에 안 보인다. 재도전이 항상 타이틀 왕복이 된다. 결국 팝업을 나중에 다시 만들게 된다

근거: GDD §14가 "본거지 HP 방식"의 결정 시점을 프로토타입 3단계로 지정했고, §12의 3단계 게이트가 "12연차 클리어율 20~35%"다. 클리어율을 재려면 종료 화면이 통계를 보여줘야 한다.

Q2. 완주 승리는 패배와 같은 화면인가

선택지트레이드오프
A. 같은 팝업, 제목만 분기 권장GetRoyalReward()가 이미 승패 구분 없이 하나의 식으로 계산한다 — 화면을 나누면 코드와 어긋난다. 완주 보너스 +6을 별도 행으로 보여주면 차이는 충분히 전달된다
B. 전용 클리어 연출/화면완주의 무게가 산다. 다만 12연차 완주를 실제로 보기 전에 만드는 연출이라 검증 없이 자산을 쓰게 된다

딸린 확인 2건

  • 완주 시 옥새 18 vs 19 — 최종 웨이브 승리 후 AdvanceWave()를 부르면 year가 13이 되어 13×1+6=19가 되고, 결과 화면도 "13/12"가 된다. 이 스펙은 부르지 않고 12에서 닫아 18로 했다. 맞는가?
  • 최종 웨이브에서 지고 끝나도 완주 보너스 +6인가 — 현재 식은 year >= yearMax만 보므로 진 경우에도 보너스가 붙는다. 붙이지 않으려면 GetRoyalReward(bool _isCleared)로 인자를 하나 받아야 한다.

Q3. 웨이브에서 패배하면 웨이브가 진행되는가 가장 중요

이 선택이 §3의 D2, 본거지 피해 수치, 최종 웨이브 패배 처리를 전부 결정한다.

선택지규칙얻는 것잃는 것 · 따라오는 결정
A. 넘어가되 본거지가 깎인다 권장 패배해도 AdvanceWave(). 본거지 −HomeDamagePerDefeat 스핀 코인이 곧 웨이브라 자원이 단조 감소해 런이 반드시 끝난다. GDD §06의 "본거지 HP −2, 다음 연차 재도전 가능"과 결이 같다. 12연차 완주율을 잴 수 있게 된다 최종 웨이브(12-3) 패배는 넘어갈 곳이 없다 → "최종 웨이브 패배 = 런 종료(미완주)"라는 예외 규칙이 반드시 따라온다(FinalDefeat). 팝업 제목 키 1개 추가
B. 같은 웨이브 재도전 웨이브 유지. 본거지 −HomeDamagePerDefeat 예외 규칙이 없다. 최종 웨이브도 HP가 남는 한 계속 도전 가능 재도전 비용을 반드시 정해야 한다(스핀 코인을 또 쓰는가?). 안 정하면 §3 D3와 합쳐져 무한 재시도가 된다. 그 수치는 GDD에 없다
C. 1단계 현행 유지(넘어가지도, 깎이지도 않음) — — 채택 불가. D2·D3에 따라 본거지 HP가 줄지 않고 같은 병력으로 무한 재전투가 되어 런이 끝나지 않는다

필요한 수치 2개 — 둘 다 GDD 미기재다.

키질문참고
HomeDamagePerDefeat웨이브 패배 1회에 본거지 몇?HomeHpMax=8이므로 1이면 8번 져야 끝나고, 2면 4번(GDD §06 외교 패배가 −2)
HomeDamagePerLeak적 1마리가 성문을 넘으면 몇?homeHit이 마릿수라 1이 자연스럽지만, 한 웨이브에 여러 마리가 새면 한 번에 여러 칸이 날아간다

Q4. 연차가 바뀔 때 외교가 끼어드는가

GDD §02는 외교를 연차의 마지막(STEP 05) 단계로, §09는 3연차부터 개방으로 못 박았다. 즉 자리는 정해져 있고, 이 문서는 그 자리(OnYearAdvanced())만 비워 둔다.

선택지트레이드오프
A. 지금은 훅 자리만 권장런이 12연차까지 도는 것을 먼저 확인할 수 있다(GDD §12의 3단계 게이트가 정확히 그것). 외교는 4단계 과제로 문서에 명시돼 있다

선택지얻는 것잃는 것
A. 씬 안에서 런만 리셋(InGameScene.RestartRun()) 권장씬 전환 비용도 커맨드 큐 위험도 없다. 즉시 다시 시작리셋 대상을 하나라도 빠뜨리면 이전 런 상태가 새 런에 남는다. 리셋 목록을 스펙에 못 박아야 한다(아래)
B. 버튼을 "타이틀로" 하나만 둔다새 코드 0줄. 위험 0재도전이 매번 타이틀 왕복 2회. 반복 플레이 흐름이 끊긴다
C. SceneManager에 재로드 지원 추가다른 씬에서도 재사용 가능Glory 공용 코드 수정. 영향 범위가 이 기능 밖으로 나간다 — 최소 침습 원칙에 어긋난다

A를 택할 경우 RestartRun()이 반드시 되돌려야 하는 것:

m_RunData.Init();            // 메타 보너스 스냅샷도 여기서 다시 뜬다(런 도중 산 것은 소급 안 됨 — 기존 주석 유지)
m_isRunEnded    = false;
m_isBattleStarted = false;
m_LastJudgeResult = null;
m_LastGrid        = null;
m_Battle.Clear();

m_SpinRoutine 정리(진행 중이면 StopCoroutine)
m_Hud.Apply(m_RunData, record);      // 핍 개수가 바뀔 수 있어 Refresh 가 아니라 Apply
m_Action.Apply(m_RunData);           // 같은 이유
m_SlotMachine 결과 표시 초기화 여부  ← 확인 필요

Hud.Apply()/Action.Apply()를 다시 부르는 이유: 둘 다 BuildPipList()로 핍을 다시 만든다. Refresh()만 부르면 이전 런의 핍 개수가 그대로 남는다.

9. GDD와의 관계

9.1 충돌 없이 추가만 하는 것

  • 전투 종료 감지 · 웨이브 정산 · 런 종료 판정 — GDD에 서술 자체가 없다(§14가 관련 항목을 "프로토타입 3단계에 결정"으로 미뤄 뒀다). 새 규칙을 넣는 게 아니라 비워둔 칸을 채우는 것이다.
  • 연차 전환 시 스핀 코인·스왑 리셋 — GDD §03 "연차 시작 시 지급, 이월 없음"의 직접 구현이다.
  • 결과 팝업 — GDD §10 ScreenZones는 HUD/REEL/BATTLEFIELD/ACTION/SIDE 다섯 영역만 정의하고 팝업 레이어는 다루지 않는다. 그 위에 덮는 팝업은 기존 세 팝업과 같은 층이라 영역 정의와 부딪히지 않는다.

9.2 이미 구현이 GDD를 앞질러 간 것 — GDD 갱신 필요

항목GDD구현제안
영구 성장 §09 "메타 진행은 종족 해금 하나로 시작. 영구 강화 트리는 초기 빌드에 넣지 않는다 — 밸런싱 축이 하나 더 늘면 프로토타입 검증이 불가능해진다" 옥새(PlayerData.m_Royal) + HouseUpgradeTable + UIHouseUpgrade 화면이 이미 존재하고, RunData.Init()이 GetRunConfigBonus()로 런 시작값에 반영한다 이 문서는 그 구현을 지우지 않는다(있는 소비처에 공급을 연결할 뿐). 다만 GDD §09를 현재 구현대로 고치는 것은 별도 작업으로 사용자 결정이 필요하다 — 밸런싱 축을 하나 더 두겠다는 판단이기 때문이다
종족 해금 §09 "각 종족의 왕을 처치할 때마다 그 종족이 플레이 가능" PlayerManager.UnlockHouse()는 있으나 호출부 0곳. 그런데 HouseTable.csv의 isUnlocked가 7종족 전부 1이라 지금은 다 열려 있다 현재 상태로는 급하지 않다. 심판/최종 웨이브 승리 시 해금 처리를 붙이려면 먼저 isUnlocked를 닫아야 하며, 그건 이 문서 밖의 결정이다
연차 = 웨이브 3개 §02는 한 연차에 전투 1회로 읽히고, §09 표는 "1–3연차 / 일반 ×3"으로 양쪽으로 읽힌다 WaveTable.csv가 12연차 × 3웨이브 = 36행으로 이미 확정. WAVE_PER_YEAR=3, 스핀 코인 1개 = 웨이브 1개 구현 쪽이 정본이다. 이 스펙은 구현을 따른다 — 이 문서에서 바꾸지 않는다
이 문서는 Assets/Design/reel_of_four_houses_GDD.html을 수정하지 않았다. 위 3건은 GDD 갱신이 필요하다는 보고이며, 실행은 사용자 승인 후 별도 작업이다.

  5. 런 종료 팝업이 뜬 상태에서 SPIN·전투 시작이 안 눌리는가
  6. 4개 언어 전부 전환해 팝업을 열어 □가 없는가(§6.4는 TTF 검사일 뿐, 실제 렌더 확인은 별도)
  7. 재시작 후 2회차 런의 HUD 핍 개수·연차·코인이 1회차 초기값과 같은가
